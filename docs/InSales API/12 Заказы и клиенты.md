# Заказы и клиенты

Это API приложения, а не сессия покупателя на витрине. Список заказов клиента после входа на сайт через `session.json` отсюда не берётся: заказы клиента читаются параметром `client_id` у `GET /admin/orders.json`.

Сверка списков по `updated_since` и `from_id` — в [изменившихся данных](03%20Получение%20только%20изменившихся%20данных.md). Скидка на отдельные строки — в [частичных скидках](04%20API%20для%20работы%20с%20частичными%20скидками.md). Скидка внешней системы — в [внешних скидках](09%20Внешние%20скидки.md).

## Заказы

`id` — идентификатор заказа в URL. `number` — номер, который магазин показывает покупателю. Номер задаётся отдельно от `id`: у заказа могут быть `id` 1 и `number` 1000, у следующего — `1001`.

`GET /admin/orders/1000.json`, где 1000 — номер, а не `id`, отвечает `404`. Тело при `Accept: application/json` остаётся HTML-страницей.

Карточка заказа собрана из полей заказа, массива `order_lines`, объекта `client`, объекта `shipping_address`, массива `discounts` и объекта `discount` — это первая скидка того же массива. У строки есть `sale_price`, `full_sale_price`, `total_price`, `full_total_price`, `quantity`, `variant_id`, `product_id`, `bundle_id`. Вложенный `client` короче карточки клиента: в нём нет `default_address`, `client_tags` и `full_name`.

`custom_status` — объект с `permalink` и `title`. `fulfillment_status` — системный статус исполнения: `new`, `accepted`, `approved`, `dispatched`, `delivered`, `returning`, `declined`, `returned`. `financial_status` — оплата: `pending`, `paid`, `partially_paid`.

### Список и число

`GET /admin/orders.json` отдаёт массив, по умолчанию 25 записей, новые `id` впереди. `per_page` больше 100 срезается до 100. `per_page=1` возвращает одну запись. `per_page=0` возвращает пустой массив.

`page` начинается с 1. Ноль отвечает `422`, тело `{"message":"page должен иметь значение, большее 0"}`.

`GET /admin/orders/count.json` считает тот же отбор и отдаёт `{"count": N}`.

### Отбор

Параметр `number` список не ограничивает. Номер читается границами `number_from` и `number_to`. Один номер — обе границы равны ему.

`from_number` оставляет заказы с номером больше либо равным переданному. Номер больше последнего даёт пустой массив.

`client_id` оставляет заказы клиента. `ids[]` повторяется для нескольких id. `fulfillment_status` сравнивается точно. `delivery_variant_id` и `payment_gateway_id` сравниваются точно. `q` — поиск магазина. Неизвестная строка возвращает `[]`.

`status=open` оставляет заказы в работе, включая доставленный и ещё не оплаченный. `status=closed` оставляет отменённые, возвращённые и доставленные оплаченные.

`custom_status` сравнивает permalink пользовательского статуса. Несколько значений передаются повторением параметра.

Одиночное `financial_status=paid` оставляет оплаченные. Любая другая одиночная строка, в том числе `pending` и `partially_paid`, оставляет заказы, у которых статус оплаты не `paid`. Точный набор передаётся массивом `financial_status[]`.

`created_at_from` и `created_at_to` запрос принимает и отвечает `200`. Выборка за календарный день, в котором заказы есть, может прийти пустой. Период по времени изменения читается через `updated_since`.

При заданном `updated_since` порядок меняется на `updated_at`, затем `id`. `per_page=1` в таком списке возвращает самый старый подходящий заказ. Следующий запрос с его `updated_at` и `from_id`, равным его `id`, этот заказ не повторяет. Дальше — алгоритм со страницы [изменившихся данных](03%20Получение%20только%20изменившихся%20данных.md).

### Создание с товаром

`POST /admin/orders.json` ждёт объект `order`. Строки — `order_lines_attributes`. Ключ `order_lines` игнорируется, и заказ без строк отвечает `422` с текстом «Заказ должен содержать хотя бы одну позицию».

В строке достаточно `variant_id` и `quantity`. Если передан только `product_id`, берётся первый вариант товара. `sale_price` в строке сохраняется и становится ценой строки. Сумма заказа считается по ней.

Адрес передаётся объектом `shipping_address`. В адресе передаётся `full_locality_name`, в ошибке оно называется «Населенный пункт». Город и регион по отдельности это поле не заменяют. Телефон и согласие на обработку персональных данных тоже обязательны, если так настроены поля магазина.

`delivery_variant_id` и `payment_gateway_id` выбирают доставку и оплату. Цена доставки при создании берётся у способа. Тариф внешней доставки и точка самовывоза передаются объектом `delivery_info_attributes`: в нём `tariff_id`, `price`, `title` и `outlet`. Для `DeliveryVariant::PickUp` в `outlet` нужны `latitude` и `longitude`, иначе ответ `422` с текстом «Не выбрана точка самовывоза». Поля доставки — в [доставке](17%20Доставка.md). Поля оплаты — в [способах оплаты](19%20Способы%20оплаты.md). Письма магазину и клиенту отключают `not_send_email_to_client` и `not_send_email_to_account`.

Клиента можно передать объектом `client` или готовым `client_id`. Вложенный `client` сохраняет имя, почту, телефон и согласие. Фамилию и отчество записывает отдельное создание клиента, после него в заказ уходит `client_id`.

Без населённого пункта и согласия ответ `422`:

```json
{
  "full_locality_name": [["Не заполнено обязательное поле \"Населенный пункт\""]],
  "consent_to_personal_data": [["Не заполнено обязательное поле \"Согласие на обработку персональных данных\""]]
}
```

### Создание с комплектом

В строку заказа передаётся `variant_id` комплекта. В сохранённом заказе строки комплекта нет. На её месте стоят составляющие, у каждой `bundle_id` равен id товара-комплекта. Количество составляющей — количество в комплекте, умноженное на количество комплектов. Цены составляющих в сумме дают цену комплекта.

Рядом может лежать тот же вариант отдельной строкой. У неё `bundle_id` пустой, а `variant_id` совпадает с составляющей. Строку для скидки поэтому выбирают по `order_lines[].id`, как в [частичных скидках](04%20API%20для%20работы%20с%20частичными%20скидками.md).

### Статусы

`financial_status: "paid"` проставляет `paid_at` и `paid_amount` по текущей сумме. `partially_paid` оплату не считает полной: `paid_at` сбрасывается. Уже записанный `paid_amount` при уменьшении заказа сам не уменьшается.

`fulfillment_status` переводит заказ в системный статус и подставляет permalink статуса по умолчанию для этого системного статуса. `delivered` заполняет `delivered_at` и ставит `custom_status` в `dostavlen` («Доставлен»).

Свой permalink передаётся в `custom_status_permalink`. Вместе с ним записывается системный статус этой записи. Системный код (`new`, `accepted`, `approved` и остальные из списка выше) в этом поле записывается как `fulfillment_status`.

Одновременно переданные несовместимые исполнение и permalink отвечают `422`:

```json
{"message": "incompatible fulfillment and custom statuses"}
```

Неизвестное исполнение отвечает `422`, в `fulfillment_status` текст «имеет непредусмотренное значение».

`version` — целое время `updated_at`. Если у заказа время больше переданного `version`, ответ `409` и тело `{}`.

В `order_changes` пишется история. У элемента есть `action`, `value_was`, `value_is`, `created_at`, `full_description` и `user_name`. Для запроса приложения в `user_name` стоит название ключа. Смена исполнения даёт `action` со значением `fulfillment_status_changed`.

### Промокод, группа и бонусы в заказе

### Дополнительное поле {#дополнительное-поле}

Список полей можно прочитать, если у приложения есть право читать заказы. Создавать и менять поле можно, если есть право на настройки магазина.

`GET /admin/fields.json` отдаёт поля заказа, клиента, адреса и контактов одним массивом. Удалённые в него не входят.

`destiny` задаёт, чьё это поле:

| Число | Куда относится |
| --- | --- |
| 1 | Адрес доставки |
| 2 | Клиент, физическое лицо |
| 3 | Заказ |
| 5 | Клиент, юридическое лицо |
| 6 | Контакты |

`destiny` `4` — строка заказа. Создание такого поля отвечает `500`, тело — HTML-страница.

Типы, которые можно создать:

* адрес: `Field::TextField`, `Field::TextArea`, `Field::Select`, `Field::Checkbox`;
* физлицо, юрлицо и контакты: те же и `Field::DateField`;
* заказ: те же, `Field::DateField` и `Field::FileField`.

`Field::Phone` и поле без `type` отвечают `404`, тело — HTML-страница. Системные поля (`system_name` заполнен) этим запросом не создаются: имя, телефон, email, населённый пункт уже есть в списке.

`handle` — латиница, цифры, `_` и `-`. Иначе `422`, тело `{"handle":["имеет неверное значение"]}`. `handle` уникален в магазине.

## Задачи пользователя {#задачи-пользователя}

Список задач можно прочитать, если у приложения есть право читать заказы. Создавать и менять задачу можно, если есть право изменять информацию заказа.

`GET /admin/user_tasks.json` отдаёт массив. В ответе нет общего числа записей. Поля: `id`, `complete`, `order_id`, `assignee_id`, `title`, `description`, `created_at`, `updated_at`, `deadline_at`, `order`. У задачи с заказом `order` — объект `{id, number}`. У задачи без заказа в списке `order` равен `null`. Автора в JSON нет.

`assignee_id` — идентификатор пользователя магазина. У запроса приложения `assignee=me` выбирает задачи с пустым `assignee_id`.

Создание отвечает `200`. Если `deadline_at` не передан, он становится временем создания плюс один час. Если `complete` не передан, в JSON стоит `null`. Явное `false` сохраняется как `false`. Фильтр `complete=false` такие `null` не возвращает. Строки `true` и `false` фильтруют. `complete=1` фильтр не включает. Если в запросе есть и `completed`, и `complete`, действует `completed`.

`order_id` и `assignee_id` сохраняются и тогда, когда заказа или пользователя нет. Тогда `order` в ответе создания отсутствует, а в списке равен `null`.

`title` обязателен, длиннее 1000 символов отвечает `422`, тело `{"title":["слишком большой длины (не может быть больше чем 1000 символов)"]}`. Пустой `title` при изменении отвечает `422`, тело `{"title":["Не заполнены обязательные поля"]}`.

## Клиенты

Карточка клиента содержит контакты, `type`, `registered`, `subscribe`, `bonus_points`, `client_group_id`, `fields_values`, `default_address`, `client_tags` и `full_name`. У физлица есть `surname` и `middlename`. У юрлица есть `inn`, `kpp`, `ogrn`, `juridical_address`, `bank_name`, `bik`, `correspondent_account`, `settlement_account`. `full_name` физлица собирается как фамилия, имя и отчество.

Запросы `orders_count=1`, `turnover=1` и `last_order=1` добавляют число заказов, оборот и последний заказ. Оборот суммирует оплаченные заказы: у клиента с неоплаченными заказами `turnover` равен `0.0`, при этом `orders_count` их считает. `last_order_id` и `last_order_number` берутся по дате создания.

### Список

`GET /admin/clients.json` отдаёт массив. Размер страницы меньше 10 поднимается до 10, больше 500 срезается до 500. В ответе есть заголовок `X-TOTAL-PAGES`.

`q` ищет подстроку в фамилии, имени, отчестве, телефоне и почте. `type=individual` и `type=juridical` различают физлицо и юрлицо. `created_at_from` и `created_at_to` ограничивают день создания. `orders_count_from` и `orders_count_to` сравнивают число заказов. `updated_since` и `from_id` работают так же, как у [изменившихся данных](03%20Получение%20только%20изменившихся%20данных.md).

### Создание

Минимальный клиент с одним телефоном создаётся. Пустое имя записывается как «Имя не указано», `consent_to_personal_data` становится `true`, `subscribe` становится `true`, `type` — `Client::Individual`. Имя и почта без телефона отвечают `422`: «Не заполнено обязательное поле "Контактный телефон"», если телефон в магазине обязателен.

Фамилия, имя и отчество все три сразу не требуются. Переданные сохраняются, `full_name` равен «Фамилия Имя Отчество», `contact_name` совпадает с именем. Повторный `GET` отдаёт те же поля. `PUT` меняет фамилию и отчество.

Юрлицо создаётся с `type` `juridical`. Обязательно `contact_name` — поле «Ваше имя». `name` сохраняется названием организации, вместе с ним записываются `inn`, `kpp` и `juridical_address`. В ответе `type` равен `Client::Juridical`.

Регистрация: `registered: true`, почта, телефон и `password` длиной от 6 символов. `skip_send_mail: true` не отправляет письмо. Пароль в ответе не возвращается. ## Теги клиентов

Тег создаётся `POST /admin/client_tags.json` с `text` и `color`. Ответ — `{"success": true, "tag": {...}}`, а не сам тег. `PUT /admin/client_tags/:id.json` отвечает `{"success": true}` и не возвращает тег. `DELETE /admin/client_tags/:id.json` отвечает тем же `{"success": true}`.

`POST`, `PUT` и `DELETE` требуют `Content-Type: application/json`, даже с пустым телом `{}`.

Список без `client_id` отдаёт теги, которые ни к кому не привязаны. После привязки тот же список стал пустым. Теги клиента читаются как `GET /admin/client_tags.json?client_id=ID` или из карточки клиента, поле `client_tags`. У элемента есть `attached`.

Привязка — `POST /admin/client_tags/:id/add.json?client_id=ID`. Снятие — `DELETE /admin/client_tags/:id/remove.json?client_id=ID`. Закрепление одного тега — `PUT /admin/client_tags/:id/attach.json?client_id=ID` с телом `{"attached": true}`. В карточке клиента `attached` становится `true`.

`GET /admin/client_tags/search.json?q=...&client_id=ID` ищет тег через поиск магазина. Сразу после создания поиск по тексту тега ещё может быть пустым. Список по `client_id` тег уже возвращает.

## Пользовательские статусы

`GET /admin/custom_statuses.json` отдаёт статусы магазина. Если свои статусы включены, а для системного статуса записи ещё нет, этот запрос создаёт статус по умолчанию. Первый список создаёт недостающие статусы.

| permalink | system_status | title |
| --- | --- | --- |
| `novyy` | `new` | Новый |

| `soglasovan` | `approved` | Согласован |
| `otgruzhen` | `dispatched` | Отгружен |
| `dostavlen` | `delivered` | Доставлен |
| `v-protsesse-vozvrata` | `returning` | В процессе возврата |
| `otmenen` | `declined` | Отменен |
| `vozvrat` | `returned` | Возврат |

## Промокоды

`GET /admin/discount_codes.json` отдаёт коды, новые id впереди. `q` ищет по коду и описанию: `q=docs` возвращает коды с этой подстрокой. Список также принимает `updated_since` и `from_id`.

Новый код по умолчанию выключен: `disabled` равен `true`, `worked` равен `false`, `act_once` равен `true`, `type_id` равен 2. Код приводится к нижнему регистру: `DOCSAPI10` сохраняется как `docsapi10`. Повтор того же кода отвечает `422`, тело `{"code":["уже существует"]}`.

`type_id` 1 — процент, 2 — сумма. Процент больше либо равный 100 не проходит проверку. `min_price` — минимальная сумма товаров. Код применяется, если сумма не ниже порога.

Чтобы код работал в заказе, в создании или в `PUT` нужно `disabled: false`. `PUT` отвечает `{"status":"ok"}`, карточка читается следующим `GET`. `DELETE` отвечает `{"status":"ok"}`.

`collection_ids` ограничивает код коллекциями. В ответе появляется `discount_collections` с `collection_id`. `discount_collections_group_id` связывает код с группой коллекций. В самом коде этого id нет: связь видна в `GET /admin/discount_collections_groups/:id/discount_codes.json`.

`worked` становится `false`, когда код выключен или одноразовый код уже использован. После заказа с `act_once: true` у кода `worked` стал `false`, второй заказ с тем же купоном не создался.

## Группы скидок на коллекции

`GET /admin/discount_collections_groups.json` и `GET /admin/discount_collections_groups/:id.json` отдают группы, которые заведены в бэк-офисе. У группы есть `id`, `title`, `collection_ids` и `collections` с `id`, `title`, `parent_id`, `permalink`. Создать или изменить группу этим API нельзя: `POST /admin/discount_collections_groups.json` отвечает `404`.

Коды, привязанные к группе, читаются отдельно.
