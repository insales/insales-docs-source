# Приложения и диалоги

Четыре ресурса: OAuth-приложения покупателя, каналы продаж приложения, действия приложения и токен канала «Диалогов».

Задачи по заказам описаны в [заказах и клиентах](12%20Заказы%20и%20клиенты.md#задачи-пользователя). Выгрузки товаров — в [выгрузках](20%20Выгрузки%20товаров.md).

Ключ доступа из раздела «Разработчикам» работает в одном магазине. Установленное приложение из каталога вызывает те же адреса своим паролем магазина. Список OAuth и токены диалогов принадлежат этому паролю: второй ключ того же магазина получает пустой список OAuth. Имя провайдера OAuth при этом одно на весь магазин.

## Права

Ключ доступа проверяет раздел настроек.

| Ресурс | Раздел ключа |
| --- | --- |
| `/admin/o_auth_apps` | настройки магазина |
| `/admin/application_actions` | настройки магазина |
| `POST /admin/dialogs/provider_tokens` | диалоги, полный доступ |

Ключ без нужного раздела отвечает `403`.

У опубликованного приложения каждое действие выдаётся отдельно. Пока действие не выдано, ответ тот же `403`. Выпуск токена диалогов в кабинете партнёра не выдаётся: опубликованное приложение на `POST /admin/dialogs/provider_tokens.json` получает `403`.

У приложения в режиме разработки первый вызов действия проходит и запоминается. Следующие вызовы этого действия идут как у выданного права.

## OAuth-приложения

Ресурс хранит `client_id` и `client_secret` входа покупателя на витрине. Установка приложения и три токена автологина описаны в [общем описании](01%20readme.md).

`GET /admin/o_auth_apps.json` отдаёт массив записей этого пароля. Пустой список — `[]`. Поля записи: `id`, `client_id`, `client_secret`, `provider`, `issuer`, `enabled`.

Готовые `provider`: `yandex`, `vkontakte`, `google`, `mailru`, `wbid`. Для них `issuer` пустой. Любое другое имя — свой провайдер, и `issuer` обязателен. Поле `enabled` в запросе не меняет запись: в ответе остаётся `true`.

Покупатель открывает `/auth/yandex`, `/auth/vkontakte`, `/auth/google` или `/auth/mailru` — магазин переходит на страницу провайдера.

## Каналы продаж {#каналы-продаж}

`GET /admin/sales_channels.json` возвращает каналы этого приложения. Каналы других приложений и каналы маркетплейсов магазина в список не входят. До первого создания список приложения пустой: `[]`.

`POST /admin/sales_channels.json` создаёт канал по `title` и отвечает `201`. В ответе `application_id` — приложение ключа, `goods_setting_type` и `goods_setting_id` пустые, `auto_export_products` равен `disabled`. Изменения канала методом `PUT` нет: такой запрос отвечает `404`.

## Действия приложения {#действия-приложения}

Действие приложения — кнопка в карточке сущности бэк-офиса. Магазин отправляет на `url` POST с телом JSON: массив выбранных объектов. `entity` задаёт, в каком разделе кнопка видна.

Читать и менять действия можно, если у приложения есть право на настройки магазина.

Список `GET /admin/application_actions.json` содержит действия текущего приложения. Действия других приложений в него не входят. Пустой список — `[]`.

`entity`: `order`, `product`, `client`, `discount_code`, `file`, `page`, `article`, `collection_filter`. У приложения должно быть право читать эту сущность. `handle` уникален в пределах приложения.

## Токен провайдера диалогов

Один метод: `POST /admin/dialogs/provider_tokens.json`. `GET` этого адреса отвечает `404`. Тело — верхний уровень, поле `messenger_type`. Обёртка `provider_token` игнорируется и отвечает тем же телом, что и пустой запрос.

Рабочие значения: `sms`, `telegram`, `viber`, `email`, `vk`. `sms` — канал «Диалогов». Код входа на витрину этим методом не выпускается.

Ответ успеха — `200` и два значения по 128 шестнадцатеричных символов. Повтор для того же `messenger_type` выпускает новую пару, старая перестаёт подходить к Provider API. Ошибки этого метода тоже приходят с `200` и полем `error`.

Удаление пароля приложения удаляет его токены. Прежний `api_token` после этого отвечает `401`.

### Provider API

Хост — `https://messengers.insales.ru`. Заголовок `Authorization` равен `api_token`, без `Basic` и без `Bearer`. Чужой токен отвечает `401`, тело `{"error":"Not authorized"}`.

Пока магазин не переключил канал на этого провайдера, `active` равен `false`. Вызов, который переключает канал, в Provider API нет.

На `send_message_url` магазин шлёт `POST` с `Authorization: webhook_token` и `Content-Type: application/json`. Текстовое сообщение:

```json
{
  "to": "chat-id",
  "internal_id": 100,
  "account_id": 233686,
  "body": "текст",
  "type": "text"
}
```

Файл вместо `body` и `type: text` приходит как `type: file` и `files: [{url, name}]`. Ответ сервиса — `200` и JSON со `status` и `external_id`. Статусы: `scheduled`, `wait_for_capture`, `complete`, `error`. Другой HTTP-статус и неизвестный `status` считаются ошибкой. Повторной отправки вебхука нет.

На `settings_url` тем же заголовком уходит `{"gateway_token":"…","account_id":233686}`, когда у магазина меняется токен шлюза.

Входящее сообщение клиента провайдер передаёт своим `POST /api/messengers/provider/v1/messages`. Пока `active` равен `false`, ответ `422`.
