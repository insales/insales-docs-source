# Приложения

В этой статье описаны OAuth-приложения для входа покупателей на витрину, каналы продаж и действия приложения в бэк-офисе.

Задачи по заказам описаны в [заказах и клиентах](12%20Заказы%20и%20клиенты.md#задачи-пользователя). Выгрузки товаров — в [выгрузках](20%20Выгрузки%20товаров.md). Токен канала «Диалогов» — в [диалогах](21%20Диалоги.md).

Ключ доступа из раздела «Разработчикам» действует в одном магазине. Приложение, установленное из каталога, обращается к тем же адресам с паролем, выданным для этого магазина.

OAuth-записи принадлежат паролю приложения, с которым созданы. Другой ключ того же магазина не видит эти записи и получает пустой список. При этом имя OAuth-провайдера должно быть уникальным для всего магазина.

## Права

При обращении по ключу доступа API проверяет, разрешён ли ему соответствующий раздел настроек:

| Ресурс | Раздел ключа |
| --- | --- |
| `/admin/o_auth_apps` | настройки магазина |
| `/admin/application_actions` | настройки магазина |

Ключ без нужного раздела отвечает `403`.

Для опубликованного приложения право на каждое действие выдаётся отдельно. Если право не выдано, API возвращает `403`.

Для приложения в режиме разработки первый вызов действия разрешается и сохраняется как выданное право. Последующие вызовы выполняются с этим правом.

## OAuth-приложения

Ресурс хранит `client_id` и `client_secret`, которые используются для входа покупателя на витрину через OAuth-провайдера. Установка самого приложения и токены автологина описаны в статье [«Как интегрироваться с InSales»](01%20readme.md).

`GET /admin/o_auth_apps.json` возвращает массив записей этого пароля. Пустой список — `[]`. Поля записи: `id`, `client_id`, `client_secret`, `provider`, `issuer`, `enabled`.

Для встроенных провайдеров используйте `provider`: `yandex`, `vkontakte`, `google`, `mailru` или `wbid`. Поле `issuer` для них пустое. Любое другое имя задаёт собственного провайдера, для которого `issuer` обязателен. Переданное значение `enabled` не меняет запись: в ответе поле остаётся `true`.

Покупатель открывает `/auth/yandex`, `/auth/vkontakte`, `/auth/google` или `/auth/mailru` — магазин переходит на страницу провайдера.

### Создание

Передайте данные в объекте `o_auth_app` или на верхнем уровне JSON. Если объект `o_auth_app` пуст, API вернёт `422` и `{"message":"param is missing or the value is empty or invalid: o_auth_app"}`.

## Каналы продаж {#каналы-продаж}

`GET /admin/sales_channels.json` возвращает каналы этого приложения. Каналы других приложений и каналы маркетплейсов магазина в список не входят. До первого создания список приложения пустой: `[]`.

`POST /admin/sales_channels.json` создаёт канал по `title` и отвечает `201`. В ответе `application_id` — приложение ключа, `goods_setting_type` и `goods_setting_id` пустые, `auto_export_products` равен `disabled`. Изменения канала методом `PUT` нет: такой запрос отвечает `404`.

## Действия приложения {#действия-приложения}

Действие приложения добавляет кнопку в раздел бэк-офиса, заданный полем `entity`. При вызове действия магазин отправляет POST-запрос на `url` приложения. Тело запроса — JSON-массив выбранных объектов.

Читать и менять действия можно, если у приложения есть право на настройки магазина.

Список `GET /admin/application_actions.json` содержит действия текущего приложения. Действия других приложений в него не входят. Пустой список — `[]`.

Поле `entity` принимает `order`, `product`, `client`, `discount_code`, `file`, `page`, `article` или `collection_filter`. Приложению нужно право на чтение выбранного типа объектов. Поле `handle` должно быть уникальным в пределах приложения.
